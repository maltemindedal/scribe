# Scribe: Building a From-Scratch Rust LLM Engine

*Project name: **scribe**. Not yet checked for availability on crates.io or GitHub.*

Building the engine is a bounded project of roughly **180 to 280 focused hours**, and the research recommends **Qwen3-0.6B** (Apache-2.0, official 639 MB Q8_0 GGUF) as the target, debugged first on three tiny models and checked layer by layer against Hugging Face float32 and llama.cpp. The difficulty lies in conventions, not mathematics: RoPE pairing, QK-norm applied before RoPE, a `head_dim` that is not `d/H`, and tokenizer defaults hidden in llama.cpp's loader each produce fluent but wrong text instead of a crash, while per-tensor quant mixes behind names like "Q4_K_M" decide which kernels must exist, so the plan is built around an automatic pass/fail test at every layer. Decode speed is a memory-bandwidth budget: Qwen3-0.6B streams about 633 MB per token, which caps decode at roughly **107 tok/s on an M1 and 242 tok/s on an M5**, so a first implementation should reach 50 to 70% of that ceiling and a tuned one, with a persistent thread pool and about five barriers per layer, 70 to 95% of llama.cpp's decode rate, while prefill (where llama.cpp uses repacked int8 kernels and Accelerate) is the larger gap. Exact tokenizer parity is achievable, since a roughly 60-line Python port of llama.cpp's byte-level BPE showed **zero mismatches against llama.cpp on 8,028 strings across four vocabularies**, and serving is a thin shell: standard-library HTTP plus `serde_json` (five crates) around one engine thread. Two tested artifacts give a head start, `gguf_check.rs` and `qk_verified_crate/`, but **all NEON code was cross-compiled and never executed**, `gguf_check.rs` fails to compile under edition 2024, and no CPU-only llama.cpp baseline for this model class was found, so every speed figure below is an estimate until a milestone-zero `llama-bench` run on the target machine.

## Qwen3-0.6B is the right target and tiny models are the right debuggers

### Why Qwen3-0.6B first

Qwen3-0.6B is a plain dense decoder with grouped-query attention at 2:1 (16 query and 8 KV heads), 28 layers, hidden size 1024, FFN width 3072, `rope_theta` 1,000,000, no rope scaling, no sliding window, tied embeddings, a 151,936-entry vocabulary and an RMSNorm epsilon of 1e-6. Its only departures from a vanilla Llama block are per-head QK-norm applied before RoPE and an explicit `head_dim` of 128 that is not `d/H` ([Qwen3-0.6B config](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/config.json), [llama.cpp qwen3.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/qwen3.cpp)). It has an official Apache-2.0 Q8_0 GGUF of 639 MB with 310 tensors (11 per layer plus two globals), which makes test loops fast ([Qwen3-0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF)). It takes the simplest correct tokenizer path (the `qwen2` pre-tokenizer with single-digit splitting, no BOS, ChatML, only six user-defined tokens), and llama.cpp's `qwen3` code path is identical for the 1.7B, 4B and 8B siblings, so quality can be scaled later without new engine code ([llama.cpp qwen3.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/qwen3.cpp)). Its weakness is capability: 0.6B is a correctness vehicle, not a product-quality model, and vendor tables show a steep capability slope in this size range (Qwen3.5 scores MMLU-Pro 29.7 at 0.8B versus 55.3 at 2B in non-thinking mode) ([Qwen3.5-0.8B README](https://huggingface.co/Qwen/Qwen3.5-0.8B)).

The alternatives lose on effort or licence rather than on interest. Llama-3.2-1B has marginally plainer attention but needs the Llama-3 frequency-scaling tensor, has roughly twice the parameters (so every debug iteration costs more), carries the Llama 3.2 Community License and shows weaker vendor-reported quality than Qwen3-1.7B and LFM2.5. Qwen2.5-0.5B is a zero-risk warm-up that shares the tokenizer and ChatML format but adds Q/K/V biases, and its official "Q4_K_M" file is mostly Q5_0 and Q8_0. **LFM2.5-1.2B-Instruct** is the recommended second model: 16 layers of which 10 are gated short convolutions and 6 are attention, per-layer KV head counts, a 65,536-entry vocabulary and the same LLAMA3-regex byte-level BPE machinery already validated, so it isolates architecture risk from tokenizer risk; its licence is the non-OSI "LFM Open License v1.0", which the research only skimmed, and its benchmark advantages are vendor-reported ([LFM2.5-1.2B README](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct), [lfm2.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/lfm2.cpp)). Gemma-3-1B comes next if SentencePiece and sliding-window attention matter (five local layers to one global, four norms per layer, head dimension 256, a 262,144-entry vocabulary and the Gemma Terms of Use), then Qwen3.5-0.8B with Gated DeltaNet layers and partial interleaved multi-section RoPE as the highest-effort target; Gemma-4-E2B adds per-layer input embeddings, shared KV layers and soft-capping and is too heavy for a first or second target ([gemma3.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/gemma3.cpp), [Qwen3.5-0.8B config](https://huggingface.co/Qwen/Qwen3.5-0.8B/blob/main/config.json), [Gemma-4-E2B config](https://huggingface.co/google/gemma-4-E2B-it/blob/main/config.json)). As of 8 October 2026 the research searches found nothing newer in the 0.5B to 1.5B dense class from Qwen, Meta, Hugging Face or Microsoft than these models.

### A debugging ladder of tiny models

Three small public models turn multi-minute debug cycles into seconds and each exposes a different bug class. `stories260K` (1.2 MB, F32, 5 layers, 8 query and 4 KV heads, a 512-token SentencePiece vocabulary, untied output, 128-token context) surfaces GQA head-mapping errors immediately and makes context-overflow paths trivial to test. `stories15M-q8_0` (26.7 MB) is the first quantised file, with multi-head attention and a 32k vocabulary. `SmolLM2-135M-Instruct` Q8_0 (145 MB, 30 layers, GQA 3:1, tied embeddings, byte-level BPE with the `smollm` pre-tokenizer, ChatML, Apache-2.0) is the first model that behaves like a chat model ([ggml-org/tiny-llamas](https://huggingface.co/ggml-org/tiny-llamas), [bartowski SmolLM2-135M GGUF](https://huggingface.co/bartowski/SmolLM2-135M-Instruct-GGUF)). The research team's advice is to avoid starting with 1B-class models, where debug cycles turn into minutes and RAM-bound CI runners (7 GB on macOS) cannot hold them. One caveat: the `smollm` pre-tokenizer was read from llama.cpp but not run through the tokenizer parity harness, so SmolLM2 token ids need their own golden test before they are trusted.

## GGUF and byte-level BPE are exact-match problems with known answers

### GGUF: a stricter format than its specification, parsed zero-copy

GGUF is still version 3 on llama.cpp master (no v4 exists): little-endian by default, `u64` counts and lengths, a header followed by key-value pairs and a tensor-info table, then zero padding to a 32-byte boundary (or `general.alignment`) and the tensor blob, with tensor offsets relative to the start of that blob ([GGUF spec](https://raw.githubusercontent.com/ggml-org/ggml/master/docs/gguf.md), [gguf.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/include/gguf.h)). The reference reader in `gguf.cpp` is stricter than the prose: it requires a power-of-two alignment, tensor names under 64 bytes, tensors laid out in info order with no gaps, no nested arrays, 1 GiB caps on strings and arrays, and no duplicate keys or tensor names ([gguf.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/gguf.cpp)). The spec also lags the code: `ggml.h` defines NVFP4 (40), Q1_0 (41) and Q2_0 (42) that `gguf.md` omits, so the type table must be built from `ggml.h`, with unknown ids a clean error rather than a panic ([ggml.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/include/ggml.h)). The recommended parse treats the file as hostile: reject implausible counts against the remaining bytes before allocating, use checked arithmetic for every offset and size, and store arrays as `(element type, length, byte range)` so a 400,000-entry vocabulary costs nothing at startup. The team's std-only parser (`gguf_check.rs`) survived 3 x 3,000 mutated or truncated real headers with no panic, hang or out-of-memory, and about 99% of mutants were rejected cleanly.

Dimensions are stored in ggml order, where `ne[0]` is the contiguous dimension, so a PyTorch `[out, in]` weight appears as `[in, out]` and each of the `out` rows is `in` contiguous elements. Quantization blocks run along that reduction axis, rows never straddle blocks, and a matvec simply streams rows from the mapping without transposing anything ([ggml.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/include/ggml.h)). Real Qwen3-0.6B shapes confirm it: `attn_q` is `[1024, 2048]`, `attn_k` and `attn_v` are `[1024, 1024]`, `attn_output` is `[2048, 1024]`, and the Q/K norm weights are `[128]`. Token embedding lookup dequantises one row of `token_embd.weight`, which touches only `n_embd/32` blocks per token, so the 165 MB Q8_0 embedding table can stay lazily paged. When `output.weight` is absent (Qwen3-0.6B, Llama-3.2-1B), the output projection reuses the `token_embd` bytes without a copy.

### Quant formats: Q8_0 first, then the Q4_K plus Q6_K pair, and read the per-tensor types

The block layouts the engine needs are small. Q4_0 is 18 bytes per 32 weights (`f16 d; u8 qs[16]`), Q8_0 is 34 bytes per 32 (`f16 d; i8 qs[32]`), Q4_K is 144 bytes per 256 (`f16 d, dmin; u8 scales[12]; u8 qs[128]`), Q6_K is 210 bytes per 256 with its scale `d` stored last, and Q8_K (`f32 d; i8 qs[256]; i16 bsums[16]`) exists only as an activation format ([ggml-common.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-common.h)). ggml pairs each weight type with an activation type: Q4_0, Q5_0 and Q8_0 weights dot against Q8_0 activations, while all K-quants dot against Q8_K, whose precomputed `bsums` feed the minimum term of Q4_K ([ggml-cpu.c](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-cpu/ggml-cpu.c)). The team's Rust dequantisers for F16, BF16, Q4_0, Q4_1, Q5_0, Q5_1, Q8_0 and Q2_K through Q6_K were **bit-exact against `gguf-py` on 25 real tensor samples and 10 randomised cases**, and the manual f16-to-f32 conversion matched numpy on all 65,536 bit patterns; Q8_K dequantisation has no independent reference and is untested.

The name "Q4_K_M" is misleading, and it determines which kernels must exist. In current llama.cpp it means Q4_K by default, Q6_K for the output (or tied embedding) tensor, Q6_K for roughly half of the `attn_v` and `ffn_down` tensors, and F32 for norms, with width fallbacks (Q4_K to Q5_0, Q6_K to Q8_0) whenever a row width is not a multiple of 256 ([llama-quant.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-quant.cpp)). The measured Llama-3.2-1B Q4_K_M is 58.4% Q4_K and 41.6% Q6_K by bytes, but the official Qwen2.5-0.5B "Q4_K_M" is **55% Q5_0, 30% Q8_0, 8.8% Q6_K and only 6.1% Q4_K**, because its width of 896 is not divisible by 256 ([Qwen2.5-0.5B GGUF](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/resolve/main/qwen2.5-0.5b-instruct-q4_k_m.gguf)). The official Qwen3-0.6B Q8_0 file is 100% Q8_0 across 197 weight tensors plus 113 F32 tensors ([Qwen3-0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/resolve/main/Qwen3-0.6B-Q8_0.gguf)). The implication is that the kernel set is driven by the target file, not the quant name: resolve the type per tensor, list unsupported types in the load error, and implement F32/F16/BF16, then Q8_0 (no bit packing, and it doubles as the activation format), then Q4_K and Q6_K together (Q4_K alone opens no real Q4_K_M file), then Q5_0 and Q4_0.

### mmap, alignment and f16 on stable Rust

Map the file read-only and private, parse the header from the mapped slice, and hand out `&[u8]` sub-slices per tensor. Either `memmap2` (which needs only `libc`) or about 40 lines of hand-declared `extern "C"` mmap/madvise/mlock/sysconf calls works; the raw version needs per-OS constants (`MADV_HUGEPAGE` and `MAP_POPULATE` are Linux-only, and `_SC_PAGESIZE` is 30 on Linux and 29 on macOS) ([docs.rs memmap2](https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html), [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)). To hand out typed blocks without undefined behaviour, define each block as a `repr(C)` struct of only `u8`/`i8` arrays (scales stored as `[u8; 2]`), which has alignment 1, no padding and no invalid bit patterns, so a `&[u8]` to `&[Block]` cast needs only a divisibility check. Weight rows sit at multiples of 18, 34, 144 or 210 bytes from a 32-byte-aligned base, so SIMD weight loads must be unaligned; only the f32 activation buffers should be explicitly 64-byte aligned. The primitive `f16` type remains unstable (E0658 on Rust 1.97 and again on 1.99.0), so conversion is hand-written or uses hardware instructions ([rust#116909](https://github.com/rust-lang/rust/issues/116909)). For cold-start latency, `madvise(WILLNEED)` or a background touch-per-page warm-up helps, `MAP_POPULATE` and `MADV_POPULATE_READ` are Linux-only, and macOS has no `MAP_POPULATE`. Sources conflict on whether transparent huge pages apply to file-backed mappings, so treat them as best-effort and measure `smaps` ([madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html), [kernel THP guide](https://docs.kernel.org/admin-guide/mm/transhuge.html)). The SIGBUS hazard when another process truncates the file is the honest reason `open` is `unsafe`.

### Hyperparameters: read them, never derive them

Read `general.architecture` first, then every hyperparameter under that prefix. The traps are in the defaults: `head_count_kv` defaults to `head_count`, the head dimension defaults to `n_embd / n_head` but Qwen3-0.6B sets `attention.key_length` to **128 while 1024/16 would give 64**, so `n_head * head_dim = 2048 != n_embd`; `rope.dimension_count` is absent from Qwen files and defaults to the head dimension; and `rope.freq_base` defaults to 10,000 ([llama-model.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-model.cpp)). Llama 3.x RoPE scaling is not in the metadata at all: it ships as an F32 `rope_freqs.weight` tensor of length `n_rot/2` that divides each pair's angle, and ignoring it silently degrades long-context quality ([conversion/llama.py](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/conversion/llama.py)). The RoPE pairing style depends on architecture: `llama` uses adjacent pairs because the converter permutes Q and K at conversion time, while `qwen2` and `qwen3` use split-half (NEOX) pairing with no permutation, so applying the wrong style gives plausible but wrong text ([llama-model.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-model.cpp)).

### Tokenizer: a hand-written pre-tokenizer plus a heap-based merge loop matches llama.cpp exactly

GGUF stores the vocabulary as parallel arrays (`tokens`, optional `scores`, `token_type`, and `merges` for BPE), but the behaviour that matters is selected by `tokenizer.ggml.pre`, a key the GGUF specification does not document, and by defaults hard-coded in llama.cpp's vocabulary loader ([GGUF spec](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md), [llama-vocab.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-vocab.cpp)). A conforming reader must replicate those defaults, not just read the keys: the Llama-3.2 GGUF has no `add_bos_token` key yet needs a BOS, while Qwen3 carries a `bos_token_id` yet must not add one, and Qwen3.5 has no BOS id at all ([Llama-3.2-1B GGUF](https://huggingface.co/bartowski/Llama-3.2-1B-Instruct-GGUF), [Qwen3-0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF), [Qwen3.5-0.8B GGUF](https://huggingface.co/ggml-org/Qwen3.5-0.8B-GGUF)). The reader should whitelist the `pre` values it supports (`qwen2`, `qwen35`, `llama-bpe`/`llama3`/`lfm2`, `smollm`, `gpt-2`) and fail loudly on the rest, as llama.cpp does. Qwen3's vocabulary is padded: ids 151,669 to 151,935 are `[PADnnn]` filler rows that exist only so the embedding matrix has 151,936 rows, and the sampler must mask them.

The pipeline for Qwen2/Qwen3, Llama 3 and LFM2 is the same five steps: partition the text at special tokens (longest first), split each raw fragment with a model-specific pre-tokenizer, map bytes to the GPT-2 unicode alphabet, run rank-ordered pairwise merges inside each pre-token, and look the results up in the vocabulary ([llama-vocab.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-vocab.cpp), [unicode.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/unicode.cpp)). llama.cpp implements the pre-tokenizer as a hand-written state machine selected by exact regex string, not a regex engine, and the three variants needed here differ in two parameters: Qwen2/3 splits digits one at a time, Llama-3 and LFM2 group up to three, and Qwen3.5 additionally treats combining marks as letters. The `regex` crate cannot express the `\s+(?!\S)` alternative and `fancy-regex` backtracks, so the recommendation is to port the state machine and use `fancy-regex` only as a dev-dependency oracle built from the regex strings in `tokenizer.json` ([regex README](https://github.com/rust-lang/regex/blob/master/README.md), [fancy-regex README](https://github.com/fancy-regex/fancy-regex/blob/main/README.md)). The merge loop is a doubly linked list plus a binary heap keyed on (rank, left index), skipping stale entries, which keeps pathological long "words" at O(n log n).

The research team tested a roughly 60-line Python port of this design against the real llama.cpp bundled in `llama-cpp-python` 0.3.36 and found **0 mismatches on 8,028 strings for four vocabularies** (Qwen3-0.6B, Qwen3.5-0.8B, Llama-3.2-1B, LFM2.5-1.2B), and 0 mismatches over an exhaustive code-point sweep of planes 0 to 3 ([llama-cpp-python](https://pypi.org/project/llama-cpp-python/)). That port is the executable specification for the Rust tokenizer and should live in the repository's `tools/` directory as the golden-file generator. Three findings from that sweep are traps worth writing into the spec. First, unassigned code points (Unicode category Cn) must be treated as plain "other" characters; treating them as unknown caused 4,494 mismatching code points for Qwen3 before the fix. Second, Hugging Face `tokenizers` applies NFC normalisation for Qwen and llama.cpp does not, so HF differs on **133 of 8,028** strings (all inputs that change under NFC, such as `e` plus U+0301); the engine should match llama.cpp, because that is what it is benchmarked against ([Qwen3-0.6B tokenizer.json](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/tokenizer.json)). Third, Rust's `char::is_alphabetic` is the Alphabetic property, not `\p{L}`, so letter, number and mark classes need `unicode-general-category` (the one justified small dependency) or generated tables, validated by the same sweep. Golden ids for Qwen3-0.6B are `"Hello, world!"` = `[9707, 11, 1879, 0]` and `"1234567890"` = `[16,17,18,19,20,21,22,23,24,15]`.

Streaming needs byte-level detokenisation: Qwen3 splits some emoji across two tokens (U+1F323 becomes `b'\xf0\x9f\x8c'` plus `b'\xa3'`), so each token decodes to bytes and only the longest valid UTF-8 prefix is emitted, with the incomplete tail held back, exactly as llama.cpp's server does ([server-common.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-common.cpp)). In the bug study of five inference engines, mis-encoded characters were the oracle behind 36% of unexpected-output bugs, which is why the research treats this as a first-class test target ([Liu et al.](https://arxiv.org/pdf/2506.09713v2)). SentencePiece (needed for Gemma 3 and Llama 2) is a separate, shorter algorithm (merge the adjacent pair with the highest score, byte fallback to `<0xNN>`); a Python port matched llama.cpp on 7,028 strings, but none of the first two targets needs it, so the tokenizer should be an enum {Bpe, Spm} with only Bpe implemented at first.

### Chat templates: hard-code the three families and verify them byte for byte

GGUF embeds the full Jinja template, but the rendered prompt for the recommended targets is simple enough to hard-code, selected by substring detection exactly as llama.cpp's non-Jinja path does (`<|im_start|>` means ChatML, `<|start_header_id|>` means Llama-3, `<start_of_turn>` means Gemma) ([llama-chat.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-chat.cpp)). The team rendered each model's real embedded template with Jinja2 and confirmed that hand-written formatters were **byte-identical for system+user, multi-turn and generation-prompt cases**. For Qwen3 the prompt is `<|im_start|>system\n...<|im_end|>\n<|im_start|>user\n...<|im_end|>\n<|im_start|>assistant\n`, no default system prompt is inserted, `enable_thinking=false` appends an empty `<think>\n\n</think>\n\n` stub, and earlier assistant turns are re-rendered without their think block. Stop on `<|im_end|>` (151645) and `<|endoftext|>` (151643) ([Qwen3-0.6B generation_config.json](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/generation_config.json)). Templates that already contain the BOS text (Llama-3.2, Gemma-3, LFM2.5) require tokenising with `add_special=false` or the prompt starts with two BOS tokens, and user-supplied content should be tokenised with special parsing off and the control ids spliced in, so that a user typing `<|im_end|>` cannot inject a turn boundary. That protection is partial, because USER_DEFINED tokens such as Qwen's `<think>` are extracted from text even with special parsing off, in both llama.cpp and HF.

## The forward pass is short and its conventions fail silently

### One pre-norm block, five conventions that fail silently

Every target is the same pre-norm block: RMSNorm, Q/K/V projections, RoPE, causal grouped-query attention, output projection, residual, RMSNorm, SwiGLU (`silu(gate) * up`, then down), residual, with a final RMSNorm and the LM head after the last layer ([llama.cpp qwen3.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/qwen3.cpp), [HF modeling_llama.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/llama/modeling_llama.py)). The family differences are small, and each is a classic wrong-output bug that raises no error. Qwen3 applies a per-head RMSNorm (weight length `head_dim`, shared across heads) to Q and K **before** RoPE; its `head_dim` is 128 while `d/H` is 64, so the attention inner width of 2048 differs from the model width of 1024 and every buffer must be sized by `n_head * head_dim`; Qwen2 has Q/K/V biases that Qwen3 dropped; the RMSNorm epsilon is 1e-6 for Qwen and 1e-5 for Llama and goes inside the square root; and GQA maps query head `h` to KV head `h / n_rep`, not `h % n_kv` ([HF modeling_qwen3.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3/modeling_qwen3.py)). The biggest trap is RoPE pairing. ggml's NORMAL type rotates adjacent pairs and NEOX pairs element `i` with `i + n_dims/2`; llama.cpp assigns NORM to the `llama` architecture and NEOX to `qwen2` and `qwen3` ([ggml.h](https://github.com/ggml-org/llama.cpp/blob/master/ggml/include/ggml.h), [llama-model.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model.cpp)). The reason is that Hugging Face permutes Meta's Llama Q/K rows into split-half layout and llama.cpp's converter un-permutes them again for GGUF, so the pairing is a property of the file, not the model name ([conversion/llama.py](https://github.com/ggml-org/llama.cpp/blob/master/conversion/llama.py)). A wrong pairing yields fluent but degrading text, and position 0 hides it because the rotation angle is zero.

The research recommends a precision policy that mirrors the reference implementations. Activations, norms, softmax, accumulators and logits stay in f32; RoPE tables are computed in f64 and stored as f32 (candle builds them in the model dtype, a pattern to avoid because angles for positions beyond a few hundred are wrong in bf16); weights are quantised blocks; and the KV cache is f32 during bring-up and f16 afterwards, converted to f32 inside the attention loop ([HF modeling_llama.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/llama/modeling_llama.py), [ggml-cpu/ops.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ops.cpp)). ggml itself sums squares in `double`, forces F32 accumulation for QK^T because "this op tends to require high floating point range", and subtracts the max logit before every `exp` ([llama-graph.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-graph.cpp), [llama-sampler.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-sampler.cpp)). The one place where a wrong precision decision stayed invisible was in a CUDA engine whose global `atomicAdd` silently dropped tiny values, raising perplexity about 5x on a 4,000-token text while short prompts looked fine, which is the argument for perplexity as a standing test ([yalm write-up](https://andrewkchan.dev/posts/yalm.html)). The research found no primary-source evidence on whether f16 activations are safe for these checkpoints, so f32 activations are a requirement, not a preference.

### KV cache: 112 KiB per token for Qwen3-0.6B, stored post-RoPE, preallocated

Preallocate per layer for the maximum context and store K after RoPE (llama.cpp rotates `Kcur` before it is cached) and V as-is. Qwen3-0.6B's 28 layers, 8 KV heads and head dimension 128 give 57,344 elements, or **112 KiB per token in f16**: 224 MiB at 2k context, 896 MiB at 8k, and 3.5 GiB at 32k, which is more than three times the 1.1 GiB of bf16 weights. Qwen2.5-0.5B, with only 2 KV heads, needs 12 KiB per token, and Llama-3.2-1B needs 32 KiB (the research team's tables, computed from the published configs; the formula reproduces kvad's reported 805 MB for Qwen2.5-0.5B at 32k in f32) ([kvad README](https://github.com/bisand/kvad)). The research favours a head-major layout `[kv_head][pos][head_dim]` for a from-scratch CPU engine, because one KV head becomes a single sequential stream for the decode loop and one pass over it can serve all `n_rep` query heads (two for Qwen3-0.6B); V stays row-major so the online-softmax accumulation is a contiguous AXPY. Neither of the first two targets needs a sliding window. A prefix-cache cap of `len - 1` applies because the last prompt token must be re-evaluated to produce logits.

### One forward() serves prefill and decode, with streaming attention and no per-token allocation

Decode streams every weight once per token at roughly 0.5 FLOP per byte, so it is bandwidth-bound; prefill reuses each weight across T tokens and becomes compute-bound. The recommended structure is a single `forward(tokens, pos0, outputs)` with T as a runtime parameter, a GEMV path for T=1, a skinny kernel for small T, a register-tiled GEMM for T of about 16 or more, chunked prefill at 256 to 512 tokens (llama.cpp's physical batch is 512), and logits computed only for the rows needed ([llama.cpp common.h](https://github.com/ggml-org/llama.cpp/blob/master/common/common.h)). The tied LM head is 15 to 28% of the weight bytes of every decode step for these models (26.1% for Qwen3-0.6B), so prefill must skip it for all but the last row; for Qwen3-0.6B that saves 155 million multiply-accumulates per skipped token. Attention uses an online-softmax kernel that never materialises the T x T score matrix ([Milakov and Gimelshein](https://arxiv.org/abs/1805.02867)), with an explicit guard against `exp(-inf - -inf)` when a row starts empty. All scratch buffers (about 70 KiB plus logits for decode, about 36 MiB for a 512-token chunk of Qwen3-0.6B) are sized once from the config, and the hot path uses only free functions over slices. The research proposes enforcing the zero-allocation property with a counting `#[global_allocator]` test that runs one warm-up token, then asserts the allocation counter stays flat across further decode steps, a prefill chunk, and the sampler including top-p. candle needed a separate "zero-allocation" decode path for exactly this reason ([candle quantized_qwen3.rs](https://github.com/huggingface/candle/blob/main/candle-transformers/src/models/quantized_qwen3.rs)).

### Sampling: copy llama.cpp's order, own the PRNG, test statistically

llama.cpp's default chain is logit bias, penalties, DRY, top-n-sigma, top-k, typical-p, top-p, min-p, XTC, temperature and a final draw, with temperature applied after truncation ([common.h](https://github.com/ggml-org/llama.cpp/blob/master/common/common.h), [sampling.cpp](https://github.com/ggml-org/llama.cpp/blob/master/common/sampling.cpp)). The first release needs only temperature, top-k, top-p, min-p, repetition/presence/frequency penalties, logit bias, a seeded PRNG and stop sequences with holdback. The penalty rule divides positive logits and multiplies negative ones by the repeat penalty, then subtracts count times frequency plus presence ([llama-sampler.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-sampler.cpp)). Do not try to reproduce llama.cpp's `mt19937` streams; use xorshift64*, PCG32 or SplitMix64 seeded per request, and verify with chi-square tests, with `top_k=1`, `temp` tending to 0 and `top_p` tending to 0 each equal to greedy. Qwen3's card recommends temperature 0.6, top-p 0.95, top-k 20 and min-p 0 in thinking mode and warns that greedy decoding "can lead to performance degradation and endless repetitions" ([Qwen3-0.6B model card](https://huggingface.co/Qwen/Qwen3-0.6B)), so golden tests use greedy for determinism while the server defaults to the vendor settings.

### Verification: a ladder where each rung has an automatic pass or fail

The research proposes a ladder that must be climbed in order. Rung 0 checks plumbing (bf16 and f16 conversions over all bit patterns, tensor shapes against the config). Rung 1 tests each op against a naive f64 reference on awkward sizes, including RoPE properties (position 0 is the identity, norms are preserved, the dot product of rotated vectors depends only on the position difference). Rung 2 compares one real layer's intermediates with a Hugging Face float32 eager run. Rung 3 runs the full model teacher-forced on fixed token ids (1, 17, 128 and 1,000 tokens) and compares the residual stream after every layer and the final logits, reporting max absolute difference, normalised mean squared error (NMSE) and top-1 agreement. Teacher forcing avoids the divergence cascade of free-running greedy comparison. Rung 4 needs no reference: logits from one prefill, from token-by-token decode and from chunks of 7, 64 and 512 must agree to about 1e-5 relative, and outputs must not depend on thread count. Rung 5 compares against llama.cpp activations on the same GGUF through `llama-eval-callback`, whose tensor names (`Qcur_normed-N`, `l_out-N`, `result_output`) the engine's debug dump should reuse; the README output is truncated, so full dumps need a small callback program ([eval-callback README](https://github.com/ggml-org/llama.cpp/blob/master/examples/eval-callback/README.md)). Rung 6 asserts 64 to 128 greedy golden tokens, requiring exact equality only where the reference top-1 margin exceeds about 1e-2. Rung 7 implements llama.cpp's perplexity protocol (non-overlapping windows, last half scored, identical BOS handling) on Wikitext-2 and, for quantised weights, the `--kl-divergence` flow ([perplexity README](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md)).

The tolerance scale comes from llama.cpp's own conversion checks: NMSE below 1e-6 is "essentially identical", below 1e-4 "excellent", below 1e-3 "very good" and below 1e-2 "good" ([check-nmse.py](https://github.com/ggml-org/llama.cpp/blob/master/examples/model-conversion/scripts/utils/check-nmse.py)). An f32 engine loading bf16 weights should land in the first two bands against Hugging Face float32 (the bf16 checkpoint upcasts exactly), an NMSE of 1e-3 to 1e-2 signals a slightly wrong epsilon, theta or scaling, and above 1e-2 a layout bug. Compare against HF in float32, never bf16, because HF's bf16 path rounds activations and RoPE tables and differs by about 1e-2 relative in logits even for a perfect engine. For quantised weights, elementwise logit comparison is meaningless; use KL divergence, where llama.cpp's README gives the noise floor (BF16 versus FP16 mean KLD 2.5e-5 on LLaMA-3-8B) and a Q8_0 reference of mean KLD about 1.4e-3 with 97.7% same-top-token, and pass within a small multiple of llama.cpp's value for the same quant. The tolerance thresholds in the ladder are heuristics from experience plus that scale, not calibrated runs.

## Decode is a 633 MB-per-token bandwidth budget that kernels and threads spend

### Roofline: Qwen3-0.6B Q8_0 streams 633 MB per token, which caps decode at 107 to 242 tok/s

Batch-1 decode reads essentially every weight once per token, so tokens per second cannot exceed memory bandwidth divided by bytes per token. For Qwen3-0.6B the tensor data in the Q8_0 file is about **633.5 MB**, of which the tied embedding and LM head is 155.6 million weights, or 26.1% of the parameters, and it is read in full by the output projection on every step (the team's arithmetic from the published config and the 639.4 MB file size) ([Qwen3-0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF)). Applying the nominal bandwidth figures gives the ceilings below; the chip bandwidths come from llama.cpp's Apple-silicon table and Wikipedia's M5 page, and the DDR5 rows are dual-channel arithmetic ([llama.cpp discussion #4167](https://github.com/ggml-org/llama.cpp/discussions/4167), [Wikipedia: Apple M5](https://en.wikipedia.org/wiki/Apple_M5), [Wikipedia: DDR5](https://en.wikipedia.org/wiki/DDR5_SDRAM)).

| Memory system | Nominal GB/s | Decode ceiling, empty context | Ceiling with a full 2k f16 KV cache |
|---|---|---|---|
| Apple M1 | 68 | 107 tok/s | 78 tok/s |
| Dual-channel DDR5-5600 | 89.6 | 141 tok/s | 103 tok/s |
| Apple M2 or M3 | 100 | 158 tok/s | 115 tok/s |
| Dual-channel DDR5-6400 | 102.4 | 162 tok/s | 118 tok/s |
| Apple M4 | 120 | 189 tok/s | 138 tok/s |
| Apple M5 | 153.6 | 242 tok/s | 177 tok/s |

The right-hand column assumes the KV cache is full at 2,048 tokens and read in full each step (235 MB at 112 KiB per token), which lowers the ceiling by 27%; at 8k context the loss is 60%. These are computed estimates, not measurements. Nominal bandwidth is also an optimistic denominator on the CPU side: AnandTech measured an M1 Max CPU cluster pulling at most about 243 GB/s of a 409 GB/s theoretical, with one core reaching about 102 GB/s and four cores 224 GB/s, so base chips with 68 to 120 GB/s are likely saturated by two to four threads, an inference rather than a measurement ([AnandTech M1 Max review](https://2fit.anandtech.com/print/17024/apple-m1-max-performance-review)). The engine should therefore report effective GB/s against a **measured** read-only streaming peak taken with its own thread pool. The research found no published CPU-only llama.cpp numbers for a 0.5B to 1B model on any Apple M-series chip, which is the largest calibration gap in the research; the only anchors are TinyLlama 1.1B Q8_0 results from 2024 builds (M2 Ultra CPU 564 tok/s prompt and 108 tok/s decode, i9-14900K 273 and 53) and Metal-path efficiencies of 77 to 87% of nominal bandwidth on base M chips, which is the team's arithmetic on a community table ([justine.lol/matmul](https://justine.lol/matmul/), [llama.cpp discussion #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). A first implementation should expect 50 to 70% of the ceiling and a tuned one 70 to 95% of llama.cpp's own decode rate.

### Kernels: the integer dot is easy, the codegen traps are not

The kernel recipe is llama.cpp's. Quantise the f32 activation vector once per matmul into the weight type's activation format (Q8_0 with scale `d = amax/127` for Q4_0/Q5_0/Q8_0 weights, Q8_K for K-quants), then compute each output row as per-block int8 dot products scaled by the two block scales and accumulated in f32: `sdot` (`vdotq_s32`) on NEON, and `sign_epi8` + `maddubs` + `madd` or `dpbusd` on AVX2 ([arm quants.c](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/arm/quants.c), [x86 quants.c](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c)). Stable Rust 1.99.0 supports the AVX2, AVX-512 and VNNI intrinsics (since 1.89), `vdotq_s32` (since 1.98) and `vcvt_f32_f16` (since 1.94). Still unstable are the i8mm intrinsics (`vmmlaq_s32`), `std::simd`, the `f16` type, `vld1q_f16`, SME and AMX detection, and `_prefetch` on aarch64, each re-confirmed as E0658 on 1.99.0; the workaround is a small `asm!` wrapper, as candle does for `sdot`, `smmla` and AMX ([Rust RELEASES.md](https://github.com/rust-lang/rust/blob/master/RELEASES.md), [vdotq_s32 docs](https://doc.rust-lang.org/stable/core/arch/aarch64/fn.vdotq_s32.html), [candle neon.rs](https://github.com/huggingface/candle/blob/main/candle-core/src/quantized/neon.rs)). On `aarch64-apple-darwin` dotprod is a default target feature, but `i8mm` (M2 and later, not M1) is not and needs runtime detection. i8mm only helps with two activation columns, so the decode path never uses it, and SME on M4 and M5 is unreachable from stable Rust except through `asm!` or FFI.

Five traps cost the research team real time and belong in the spec. First, the f16 block-scale conversion: the natural `_mm_cvtph_ps(_mm_cvtsi32_si128(h))` made LLVM emit `vpinsrw` with the f32 accumulator as merge source, adding a false loop-carried dependency, so the single-row Q4_0 kernel ran at 3.6 GB/s instead of about 9 GB/s, **2.4x slower than the same loop in C**; forcing `vmovd` plus `vcvtph2ps` through `asm!` fixed it, after which Rust matched a C transcription of llama.cpp's loops within noise (Q8_0 about 22 GB/s, Q4_0 about 8.7 GB/s in L2). The `half` crate's `to_f32` compiled to an out-of-line runtime-detection call when F16C was not enabled globally. Second, the AVX2 sign trick breaks on the pair (-128, -128), so activations must be clamped to [-127, 127], exactly why ggml's Q8_K quantiser uses `-127/max`; a differential fuzz target found this within 40 seconds when the clamp was removed ([ggml-quants.c](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-quants.c)). Third, ggml's scalar quantiser rounds ties away from zero while its SIMD quantisers round ties to even, so use `f32::round_ties_even` in both or compare with a one-step tolerance. Fourth, f32 reductions do not auto-vectorise in Rust because LLVM may not reassociate, so use `algebraic_*` operations (stable since 1.98) or manual lane arrays, and avoid bounds checks with `chunks_exact` or `as_chunks`. Fifth, a `#[target_feature]` helper called from a function lacking the feature is not inlined (a `bl` per iteration with no `sdot` on baseline aarch64 Linux), so every helper must carry the same feature string as its caller and the row loop must live inside the feature-enabled function; dispatch once through function pointers, which measured within noise of direct calls.

For the matvec structure, the research recommends sharing one quantised activation across the Q/K/V projections and across gate/up, giving each thread a contiguous band of output rows (multiples of 4 and of 16 floats so no two threads write one cache line), and computing four weight rows per call so the activation block stays in registers. In the team's x86 measurements the four-row Q8_0 kernel gained 1.2x in L2 and 1.0 to 1.2x on a DRAM-sized set, while Q4_0 gained 1.2 to 1.3x in cache and 1.7 to 1.8x on DRAM; an earlier 2 to 3x result was retracted as an artifact of the slow baseline. Weight repacking (llama.cpp's 4x4, 4x8 and 8x8 interleaved layouts; candle's 16-row VNNI tiles) mainly speeds prefill, with Arm reporting roughly 2 to 2.5x and testers seeing small decode gains on an M2, higher load time, and in one Android report doubled memory ([llama.cpp PR #5780](https://github.com/ggml-org/llama.cpp/pull/5780)). The recommendation is to skip repacking at first and use token tiling for prefill (reuse each unpacked weight block across two to four activation columns), then revisit. Non-matmul kernels port llama.cpp's `ggml_v_expf` (2 ulp measured against f64), which also makes cross-checking against llama.cpp's logits easier ([vec.h](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/vec.h)).

### Threading: a persistent pool with about five barriers per layer, not rayon per operation

Decode is a chain of microsecond-scale operations. At 100 GB/s, streaming one Q8_0 attention or FFN matrix of Qwen3-0.6B takes about 11 microseconds (K and V), 22 microseconds (Q and O) and 33 microseconds (gate, up, down) by the team's arithmetic, so a synchronisation costing 1 to 2 microseconds is a visible tax. llama.cpp runs the whole graph SPMD: every thread walks every node, with the caller as worker 0, and meets at a spinning atomic barrier after each node, which the research estimates at roughly 500 barriers per token for a 24-layer model; workers poll for the next graph before sleeping ([ggml-cpu.c](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c)). Its matmul splits rows statically when there are fewer than four chunks per thread and with an atomic chunk counter otherwise. The Rust design the research proposes is a persistent pool of N-1 workers plus the caller, a sense-reversing barrier on 128-byte-padded atomics (`crossbeam`'s `CachePadded` uses 128 bytes on x86-64 and aarch64), a wall-clock spin window followed by park, static row partitioning with a dynamic tail counter, and fused regions so that a layer needs about five barriers (QKV with redundant per-thread RMSNorm, attention by head, output projection, gate/up with the SwiGLU epilogue, down projection), roughly 140 per token for 28 layers ([crossbeam cache_padded.rs](https://github.com/crossbeam-rs/crossbeam/blob/master/crossbeam-utils/src/cache_padded.rs)). The `unsafe` core is a `Shared<T>` output wrapper handing out provably disjoint ranges from a pure, property-tested partition function.

The evidence against fork-join per operation is consistent. Frink, a Rust GGUF engine, reached decode parity with llama.cpp on Metal but ran **1.4 to 5.1x slower on CPU**, which its author attributes to rayon fork/join per operation ([Frink write-up](https://www.fratepietro.com/2026/frink-rust-gguf-inference-engine/)). Gendignoux measured rayon delivering only 2x on eight threads with about 65,000 `sched_yield` and 5,000 `futex` calls, and found a custom pool with pinning 10 to 20% faster ([Gendignoux](https://gendignoux.com/blog/2024/11/18/rust-rayon-optimized.html)). Rayon is acceptable as the correctness-milestone stepping stone, and the team recommends measuring an empty-region round trip at 2, 4 and 8 threads (hot and after 1 ms idle) as the quantitative justification for the custom pool; the claimed 10 to 40% decode gain is an estimate. Platform specifics matter. Apple provides no affinity API (`THREAD_AFFINITY_POLICY` returns `KERN_NOT_SUPPORTED` and ggml's affinity code is a no-op on Apple), so use the performance-core count from `sysctl hw.perflevel0.physicalcpu` rather than `available_parallelism()` (which counts efficiency cores), declare `pthread_set_qos_class_self_np` yourself because the `libc` crate lacks it, and sweep thread counts because M5 Pro and Max replace efficiency cores with "super" and "performance" cores, so the old rule needs re-validation ([Apple Developer Forums](https://developer.apple.com/forums/thread/703361), [Eclectic Light](https://eclecticlight.co/2024/06/20/making-apple-silicon-faster-2-multithreading/), [Apple Newsroom](https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/)). On x86 use physical cores, pin with `sched_setaffinity`, and note that NUMA interleaving doubled decode on dual-socket servers in a community report; SMT does not help decode ([llama.cpp issue #1437](https://github.com/ggml-org/llama.cpp/issues/1437)).

### Benchmarking against llama.cpp: two builds, thread sweeps, interleaved runs, honest ratios

The fair baseline on a Mac is two llama.cpp builds: a pure-ggml CPU build (`-DGGML_METAL=OFF -DGGML_BLAS=OFF -DGGML_ACCELERATE=OFF`) and the default CPU build in which Accelerate may use the AMX coprocessor for prefill, because Metal and Accelerate are on by default ([llama.cpp build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)). Three traps are specific to llama.cpp. If `SOURCE_DATE_EPOCH` is set in the environment, `GGML_NATIVE` silently turns off, so the build must be checked via its `system_info` line. Q4_0 gets online-repacked 8x8 kernels on AVX2 while Q8_0 does not in the master the team read, so a Q4_0 comparison pits the engine against repacked kernels and a Q8_0 comparison against plain vec-dot. And `llama-bench` excludes tokenisation and sampling and uses one thread count for both prompt and generation, so the engine's timer should do the same ([llama-bench README](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)). The run recipe is `llama-bench -p 512 -n 128 -r 15 --delay 5 -o json` on the identical hashed GGUF, a thread sweep for each side's best, `-pg 512,128` as an end-to-end check, and `-d 0,512,2048` for decode against depth. Runs should be interleaved A,B,A,B after one discarded warm-up, on AC power with Low Power Mode off (a community Metal run lost 22% prompt and 39% decode speed in Low Power Mode), with at least 10 repetitions, median and interquartile range, and a bootstrap 95% confidence interval on the ratio of medians; differences inside run-to-run noise are ties. A faster-but-wrong engine is not comparable, so the verification ladder runs first, and the report states the llama.cpp commit, flags and `system_info` line.

| Stage | What it is | Decode | Prefill pp512 | Main limiter |
|---|---|---|---|---|
| S0 | Scalar f32 reference | 1 to 5 tok/s | Same as decode | Dependent f32 chains, about 2 GB per token |
| S1 | Scalar quantised | 3 to 30 tok/s | Same as decode | Dequantisation compute |
| S2 | Single-thread SIMD | 30 to 100 tok/s; at least 20% of llama.cpp | 60 to 200 tok/s | Single-core bandwidth, then compute |
| S3 | SIMD plus rayon or scoped threads | 50 to 150 tok/s; at least 50%, may regress on small matrices | 250 to 800 tok/s | Region overhead, wake-up jitter |
| S4 | Persistent pool, fused regions | 70 to 95% of llama.cpp | 40 to 90% of the pure-kernel build | DRAM bandwidth (decode), int8 throughput (prefill) |

These stage figures are the research team's estimates for Qwen2.5-0.5B on base-to-Pro Apple silicon (absolute S4 decode of about 50 to 120 tok/s at Q8_0), not measurements, and they must be re-based by a milestone-zero `llama-bench` run on the actual machine. Prompt processing is compute-bound and CPU-only llama.cpp reaches prompt-to-decode ratios of only 3 to 20x; matching the default Mac build's Accelerate prefill without writing AMX or SME code is probably out of reach, so pp should be reported against both builds.

## One engine thread behind a thin HTTP shell serves OpenAI clients

### The wire contract is small, and the openai-python SDK is the compatibility oracle

The hard contract is `POST /v1/chat/completions` (one JSON object, or an SSE stream of `chat.completion.chunk` objects ending in `data: [DONE]`), `GET /v1/models`, nested `{"error": {...}}` bodies with correct HTTP statuses, and llama.cpp's `GET /health` (503 while loading, 200 `{"status":"ok"}` when ready) ([OpenAI streaming reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events), [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). The research verified from the SDK source what clients really parse: a chunk needs only `id, object, created, model, choices[].index, choices[].delta`; the stream stops at any `data:` payload that starts with `[DONE]`; comment lines beginning with `:` are ignored, so keep-alives are safe; and any in-stream JSON with a truthy `error` key raises an exception ([openai-python chat_completion_chunk.py](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/chat_completion_chunk.py), [openai-python _streaming.py](https://github.com/openai/openai-python/blob/main/src/openai/_streaming.py)). With `stream_options.include_usage`, the server sends one extra chunk before `[DONE]` whose `choices` is an empty array and whose `usage` covers the request, and every earlier chunk carries `"usage": null` ([openai-python stream options](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/chat_completion_stream_options_param.py)). SSE framing follows the WHATWG rules: `text/event-stream`, events end on a blank line, and a comment keep-alive every 15 seconds or so protects against proxies that drop idle connections ([WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)).

Two design rules follow. Do all validation, templating, tokenisation and context-length checks before writing the 200 header, so errors can still be returned as proper 4xx JSON; afterwards errors can only be signalled in-band as `data: {"error": {...}}`. And treat `model` as an echo field rather than a lookup key, since many clients send placeholder names. The OpenAI reference pages the team fetched were truncated before the parameter list, so the exact limits (`stop` of at most 4 entries, `logit_bias` range, penalty ranges) are background knowledge, not verified. The acceptance matrix is `curl -N`, openai-python sync and async with and without `include_usage` (including an early `break` that must cancel generation), and Open WebUI in Docker, which needs `/v1/models` and `/v1/chat/completions` and whose stop button exercises client abort ([Open WebUI docs](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible)).

### HTTP stack: std plus serde_json is five crates; axum is up to fifty-four

Because the engine thread is the only real bottleneck and concurrency is a handful of connections, a blocking HTTP/1.1 server on `std::net` (thread per connection, a few hundred lines, `Connection: close` on every response, chunked encoding for streams, flush after each event) is the best fit for the project's ethos. The team measured transitive dependency counts with `cargo tree` on 2026-10-08: **5 crates for `serde_json`, 22 for hyper 1 plus tokio, 39 to 54 for axum**, and `half` alone drags in `zerocopy` and the `syn` stack, so f16 conversion should be hand-written ([crates.io hyper dependencies](https://crates.io/api/v1/crates/hyper/1.12.0/dependencies), [crates.io half](https://crates.io/crates/half)). `tiny_http` is rejected because its last stable release dates from 2022 and it owns the socket, which makes disconnect detection awkward ([crates.io tiny_http](https://crates.io/crates/tiny_http)). The ecosystem alternative is hyper 1.x without axum, bridged to a dedicated engine `std::thread` through a channel, never `spawn_blocking` ([Tokio bridging guide](https://tokio.rs/tokio/topics/bridging)). Because the server crate is isolated behind the engine's channel API, std and hyper can be swapped without touching the engine. Client disconnect is the subtle part: write errors on the next flush set a cancel flag, which is near-immediate during decode; during a long prefill nothing is written, so the HTTP thread must poll the socket (a non-blocking `peek` returning `Ok(0)` means the peer closed) between prefill chunks ([Rust users forum on axum SSE disconnects](https://users.rust-lang.org/t/how-to-detect-an-a-dropped-sse-server-sent-event-client-using-axum/101028)).

### One engine thread owns the model, KV caches and sampler state

The runtime shape is copied in miniature from llama-server: HTTP worker threads do parsing, templating and tokenisation, and a single engine thread owns the weights, the KV-cache "slots" and every sampler's RNG, communicating by bounded channels ([llama.cpp server README-dev](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)). The engine never blocks on a slow client (it uses `try_send` into a bounded per-request channel and cancels on overflow), weights are an immutable `Arc<Model>` over the mmap, and each slot carries its own cache, scratch buffers, token history and sampler state, which avoids the shared-sampler bug class documented in llama.cpp issue #3537 ([Liu et al.](https://arxiv.org/pdf/2506.09713v2)). Phase one is a single slot with serialised requests and a queue depth of eight (the ninth gets 503 with `Retry-After`). Phase two adds N slots with a **longest-common-prefix prompt cache**: a chat client resends the whole history every turn, so reusing the slot whose cached token ids share the longest prefix turns O(history) prefill into O(new message). The cap `keep = min(lcp, n_prompt - 1)` is essential because at least one token must be evaluated to produce logits. Continuous batching across slots is the stretch goal and the only multi-request design that raises aggregate decode throughput on a bandwidth-bound CPU, because several sequences can share one pass over the weights; it needs small-batch matmul kernels, so it is out of scope for the first release ([yalm write-up on bandwidth-bound decode](https://andrewkchan.dev/posts/yalm.html)).

Context policy is explicit: reject with 400 `context_length_exceeded` when the prompt does not fit, clamp `max_tokens` to the remaining window and finish with `"length"` when it fills, and compute `KV bytes = 2 * n_layer * n_kv_head * head_dim * n_ctx * sizeof(elem) * n_slots` at startup so the process can refuse to start over a memory limit. The suggested workspace has nine crates: `gguf`, `tokenizer`, `kernels` (block types, SIMD, thread pool), `model` (config, weights, forward, KV cache), `sampler`, `engine` (slots, prefix cache, scheduler, no HTTP or JSON), `server` (the only crate allowed `serde_json`), `bench` and `cli`, with `unsafe` confined to `kernels` and each SIMD path tested against a scalar oracle. A CI matrix of `ubuntu-latest` (x86-64) and `macos-latest` (arm64) runs correctness tests only, never performance, on the small models (macOS runners have 3 cores and 7 GB) ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Observability mirrors llama.cpp's vocabulary so numbers compare directly: a `timings` object per response, `/metrics` counters, a `--bench` mode that reproduces `llama-bench`'s `pp`/`tg` columns, a feature-gated per-op profiler, and a `dump-logits` subcommand that is the main parity-debugging tool ([llama-bench README](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)).

## Ten milestones and 180 to 280 hours reach a defensible benchmark

The serving research proposed ten milestones totalling **177 to 282 focused hours** (the sum of its table), roughly 5 to 9 months at 8 hours a week; those hours are the research team's judgment for a strong Rust developer new to ML internals, with no published effort data for comparable projects, and the acceptance thresholds are proposals rather than measured values. The two schedule risks the research names are tokenizer and pre-tokenizer parity (M1) and "nearly right" numerics in the first forward pass (M2). Two stretch features have a poor payoff-to-effort ratio for the headline benchmark and should not be scheduled early: n-gram speculative decoding does not move a random-token `tg128` benchmark at all, and the research judges that draft-model speculation is unlikely to help a 0.6B target because no sensible sub-100M draft model exists for the Qwen family. Prefix caching, in contrast, is cheap and gives the largest user-visible improvement in time to first token for chat. Model files stay out of the repository (an `xtask` downloads them with a pinned revision and SHA-256), each model's licence is recorded in a `MODELS.md`, and CI runs correctness tests only on the small models, with performance in a separate manual workflow.

## Two tested artifacts start the work, and the NEON code has never run

### Starting artifact one: gguf_check.rs

`/home/claude/research_notes/Rust LLM inference engine/gguf_check.rs` is a roughly 470-line, std-only file containing a hardened GGUF v3 parser (checked reader, arrays kept as byte ranges, 15 ggml types, counts validated against remaining bytes before allocation), align-1 `repr(C)` block structs behind an `unsafe trait Block` and `cast_blocks`, scalar dequantisers, a manual f16 and bf16 conversion, a raw-libc mmap wrapper with `madvise`, `mlock` and page-size helpers, and a CLI with `f16`, `dequant` and `parse` subcommands (the last includes a 3,000-case mutation fuzz). It is the proposed starting point for the `gguf` crate. On the research team's re-run it parsed a fresh Qwen3-0.6B header (310 tensors, 28 key-value pairs, 151,936 tokens) and its fuzz run parsed 22 mutants, rejected 2,978 and never panicked. The caveats are concrete: it compiles with `--edition 2021` but **fails under edition 2024** ("extern blocks must be unsafe" at line 385; the fix is `unsafe extern "C"`); it is Unix-only (Linux and macOS constants); Q8_K dequantisation is untested because `gguf-py` has no reference for it; it has no IQ, MXFP4 or ternary types; big-endian files are unsupported; it rejects invalid UTF-8 strings, which may be stricter than some community files need; and it accepts non-consecutive tensor offsets where the reference reader does not.

### Starting artifact two: qk_verified_crate

`/home/claude/research_notes/Rust LLM inference engine/qk_verified_crate/` is a package named `qk` (edition 2024, `rust-version = "1.99"`, fat LTO) holding the quantised-dot and vector kernels. `src/lib.rs` has block types for Q4_0, Q8_0, Q4_K, Q6_K and Q8_K, scalar reference dots, a hand-rolled f16 conversion, AVX2 and AVX-VNNI kernels (single-row, four-row and GEMV drivers for Q8_0 and Q4_0, plus Q4_K and Q6_K), a `neon` module with Q8_0 and Q4_0 kernels, a 2x2 `smmla` tile through `asm!` and a prefetch wrapper, and `select_dot_q8_0()` runtime dispatch. `src/vecops.rs` has `expf8`, softmax, RMSNorm, NEOX RoPE and an f32-by-f16 dot, with NEON counterparts. The crate also ships a kernel benchmark, a feature-probe binary, a differential fuzz target with a `no_clamp` feature that reproduces the sign-trick bug, a C transcription of llama.cpp's AVX2 loops for Rust-versus-C comparison, and a `half` crate inlining check. The research team reproduced its 12 passing tests on Rust 1.97.0 (with `--ignore-rust-version`) and 1.99.0, a successful `aarch64-apple-darwin` cross-compile whose assembly contains `sdot`, `smmla` and `fcvt` instructions, the bench trends (four-row Q4_0 at 4.05 GB/s versus 2.34 for one row at DRAM size), and the stability claims for `f16`, `std::simd`, AMX detection and `vmmlaq_s32`.

Its caveats matter more than its successes. **All aarch64 code, including every NEON kernel, the `smmla` tile and the NEON vector ops, was cross-compiled and inspected but never executed**, and Miri cannot run it either, so the first task on Apple hardware is to run the same scalar-reference tests against `neon::*`. There are no NEON Q4_K or Q6_K kernels and no complete i8mm dot kernel. The `vdotq_s32` path needs Rust 1.98 or newer. Its block structs store scales as `u16` (alignment 2) whereas `gguf_check.rs` uses `[u8; 2]` (alignment 1), so the two should be unified; `[u8; 2]` removes the alignment question for mmap casts, though in real files all block sizes are even and tensor bases 32-byte aligned (an inference, not a tested claim). The "C" baseline is the team's transcription of llama.cpp's loops, not llama.cpp itself, and all x86 timings come from a noisy 2-vCPU Xeon VM, so only same-run ratios mean anything. The tokenizer's Python oracle is not a separate file: its tested reference code lives inside `tokenizer_and_models.md`, in the same research folder as the two artifacts (the BPE splitter and merge loop in section 2, the SentencePiece port in section 3), and should be extracted into the repository's `tools/` directory.

## Conclusion

The research changes the shape of the project more than its size. The kernels, which look like the glamorous part, are the best-understood: the llama.cpp recipe ports to Rust one-to-one, a C-versus-Rust comparison on x86 closed to within noise once a single instruction sequence was fixed, and the ceiling is set by DRAM. The risk sits in the verification infrastructure around them. The one measured kernel failure, a 2.4x slowdown from a false register dependency, passed every correctness test and was visible only because an independent C baseline ran in the same harness; the one measured correctness failure, the AVX2 sign trick on -128 activations, was found only because a fuzz target was run with the clamp deliberately removed. The practical rule is that every kernel needs a same-harness baseline it was not written against, every oracle choice needs a written reason (llama.cpp versus Hugging Face already disagree on 133 of 8,028 Qwen strings because of NFC), and every green check needs a demonstration that the check can fail.

What the benchmark claim can honestly be is also narrower than the brief suggests. Because decode is bandwidth-bound for both programs, the defensible headline is the fraction of a measured streaming peak that the engine reaches next to the fraction llama.cpp reaches on the same file, not a bare tok/s ratio, and prefill should be reported against two llama.cpp builds because the default Mac build gains from a matrix coprocessor that stable Rust cannot reach. Two things would change the plan: a real-hardware run of the NEON tests that fails (the largest untested assumption in the starting code), and a milestone-zero `llama-bench` that shows llama.cpp already near the bandwidth ceiling on the target Mac, which would make the 70 to 95% decode target mostly a measurement-noise question and shift the project's value toward the verification suite and the server.
